## Rationale (key decisions & agent decision log)
- Prototype implemented as a single Python process using only the standard library (http.server for HTTP, sqlite3 for persistence, threading for background sweeper/analytics writer) — no external frameworks or services.
- SQLite file (url_shortener.db) is the durable store for urls, analytics_events, and api_keys tables; WAL mode enabled for better concurrent read/write behavior within the single process.
- Short codes generated as base62 encoding of the SQLite auto-increment row id (padded to min 6 chars) by default; custom aliases validated for uniqueness against the same short_code unique index before insert.
- Duplicate long_url submissions: policy is 'return existing short code' — a hash (sha256) of the normalized long_url is stored and indexed so creation first checks idx_urls_long_url_hash and returns the existing mapping unless a custom_alias is explicitly requested (which forces a new row).
- Redirect path checks an in-process LRU cache (dict-based, capped size e.g. 100k entries) before falling back to SQLite; cache populated on read-through and invalidated by the expiration sweeper thread.
- Analytics events are recorded by pushing a lightweight event dict onto an in-memory queue.Queue immediately after cache/DB lookup succeeds, so the redirect response (302) is returned before the event is persisted; a single background thread drains the queue and batch-inserts into analytics_events.
- TTL support implemented via nullable expires_at column; a background sweeper thread runs periodically to mark/delete expired rows and purge them from the cache, and the redirect handler also checks expiry defensively on each lookup.
- Input validation enforces scheme in {http, https}, max URL length 2048, rejects loopback/private-network hostnames (e.g., localhost, 127.0.0.1, 169.254.x.x, RFC1918 ranges) to mitigate open-redirect/SSRF-style abuse.
- Rate limiting implemented as an in-memory token-bucket keyed by API key (or client IP if no key), sufficient for single-process prototype; API keys are optional and generated via the /api/v1/keys convenience endpoint.
- Target architecture named by the requirement (Postgres for persistence, Redis for caching, containerized deployment) is recorded as the production evolution path; the first runnable slice substitutes SQLite + in-memory structures to stay within the stdlib-only constraint.
- OpenAPI spec authored as a static JSON/YAML file checked into the repo and served at /openapi.json, hand-maintained rather than generated by a framework.
- Persistence default: sqlite (NFRs imply durability/scale -> recommend the SQLite backend as default).

- Static safety (first, before anything runs): an AST scan rejects dangerous calls (eval/exec/os.system/shell=True/pickle, import aliases resolved), imports outside the standard library, hard-coded secrets and modules that shadow the standard library; code with a high-severity finding is not executed.

- Contract: an OpenAPI document must exist whenever the design exposes an API (existence is checked, not conformance).
- Documentation: README/architecture docs must be present.
- Feedback loop: repairable findings are fixed by the Repair agent and re-validated (bounded); compile failures halt for human attention.

## Risks
- Persistence: an in-memory store (data lost on restart) or SQLite (single file, single node) where configured; a multi-node deployment needs an external database.
- Authentication and rate limiting in the generated slice are in-process prototypes: state resets on restart and is not shared across instances.
- Generated tests cover core paths; add load/security tests before production.

## Trade-offs
- Prototype uses SQLite with WAL mode on a single process; production would use PostgreSQL with primary/replica replication and connection pooling to support horizontal read scaling and durability guarantees beyond a single disk.
- Prototype caches hot short_code lookups in an in-process Python dict limited by process memory and lost on restart; production would use a distributed cache (e.g., Redis) shared across API instances for consistent, larger-capacity, crash-resilient caching.
- Prototype defers analytics writes via an in-memory queue.Queue drained by one background thread, risking event loss on process crash; production would use a durable message broker (e.g., Kafka/SQS) to guarantee at-least-once delivery of click events to an analytics pipeline.
- Prototype serves all traffic from one Python process via http.server, limiting throughput to a single core; production would run multiple containerized API instances behind a load balancer for horizontal scalability and high availability.
- Prototype enforces rate limiting with per-process in-memory token buckets, which resets on restart and doesn't coordinate across instances; production would centralize rate-limit state in a shared store (e.g., Redis) for consistent enforcement across a fleet.
- Prototype relies on a periodic background thread to sweep expired URLs, introducing a delay between expiry and cache/DB cleanup; production could use TTL-native store features (e.g., Redis EXPIRE, DB partition pruning) for more immediate and efficient expiration.
- Prototype terminates plain HTTP for simplicity in local runs; production would enforce HTTPS via a TLS-terminating load balancer/reverse proxy and HSTS headers.

## Assumptions
- What is the expected scale (requests per second, total URLs stored) the system must support? -> assumed: Design for moderate scale initially (up to a few thousand requests/sec, tens of millions of URLs), using a relational DB (e.g., Postgres) with a cache layer (e.g., Redis) for redirects, architected to scale horizontally later
- Should the service support user authentication and per-user URL management, or is it fully public/anonymous? -> assumed: Build as a public API without authentication for the prototype; add an API key mechanism for rate limiting/tracking usage
- What level of analytics detail is required (basic click counts vs. geolocation, device breakdown, referrer analysis)? -> assumed: Track basic analytics: total clicks, timestamp per click, referrer, and user-agent; expose aggregated counts via API
- Should shortened URLs expire by default or persist indefinitely? -> assumed: URLs persist indefinitely by default, with an optional TTL parameter at creation time
- What technology stack/language and deployment environment should be used? -> assumed: Use a standard modern stack (e.g., Node.js/Python/Go backend, PostgreSQL for persistence, Redis for caching), deployable via containers (Docker)

## Limitations
- Reasoning and code authoring were model-driven; no stage needed the deterministic fallback.
- The design decisions under Rationale describe the model's target design. What is verified for the generated slice is: the endpoints marked 'yes' in the coverage table exist in the code, the code compiles, passes the static scan, and passes the model's own tests. Individual decisions (e.g. an async queue, a required header) are not checked against the code; a critic agent that does so is the next step. The API contract and README are synthesized from the design by the Repair agent when the model's bundle does not include them.
- Generated service targets clarity and the standard library over framework features (e.g. no async, no ORM).
- Run in the GitHub Actions pipeline: the in-run gates were automatic (they never accept a failing report); human approval happens at the pipeline's GitHub Environment gates - spend before the run, acceptance of this result after it.
- The validation sandbox is an isolated-mode subprocess with a timeout and a scrubbed environment, not a network-isolated container or separate OS user.
